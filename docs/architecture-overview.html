Bản đồ kiến trúc Burndown Engine

Một monorepo pnpm gồm 3 ứng dụng và 4 gói thư viện. Nó đọc dữ liệu từ Jira, tính "khối lượng còn lại theo ngày" và trạng thái Signboard trong một lõi tính toán thuần, rồi phục vụ biểu đồ cho web. Xương sống là một quy tắc: phụ thuộc chỉ đi một chiều.

03

Front-end & back-end nối với nhau thế nào

Web không bao giờ gọi thẳng Jira hay DB. Nó chỉ nói chuyện với API qua HTTP /api, và cả hai đầu chia sẻ cùng một bộ schema zod.

  1. Component → hook. Màn hình dùng hook use-*.ts (TanStack Query). Không component nào tự gọi fetch.
  2. Hook → client.ts. Nơi DUY NHẤT gọi fetch: ghép URL /api/…, gửi kèm cookie phiên, đổi mọi lỗi thành ApiError.
  3. Qua cổng. Dev: Vite proxy /api → localhost:3000, đóng vai cổng SSO (chèn x-user-id). Prod: auth proxy thật đứng trước.
  4. Fastify phân giải danh tính. Hook onRequest tin danh tính header, rồi tra vai trò ở bảng app_user — không tin role client gửi.
  5. Route gọi lõi. Mỗi route nhận "port" đã tiêm; gọi engine/db. Route chỉ điều phối, không chứa logic nghiệp vụ.
  6. Trả về & kiểm biên. API trả JSON; client.ts validate bằng zod ngay tại biên rồi trả object đã kiểu hoá. TanStack Query lo cache & retry.
Hợp đồng zod

Cùng một schema trong packages/shared validate ở cả hai đầu — API kiểm đầu ra, web kiểm đầu nhận. Web alias thẳng vào mã nguồn shared, nên sửa schema một chỗ là front-end thấy ngay, không build lại.

Bảo mật SSO

API không tự đăng nhập người dùng. Cổng SSO đặt header x-user-id = email đã xác thực và xoá mọi x-user-* mà client tự khai. Đây cũng là lý do dev shim danh tính nằm ở Vite proxy, không ở API.

04

Luồng dữ liệu: tách đường ghi và đường đọc

Việc dài hơi (gọi Jira, tính toán) đẩy hết vào worker và ghi sẵn kết quả xuống Postgres. Request đọc của web chỉ lấy số đã tính — nhanh, không chạm Jira.

Ghi Worker → Postgres

Chạy nền, mỗi lượt vài phút. Kích hoạt: cron đêm 00:01, resync tay, quét dirty:epics mỗi giờ (:15), đối soát CN 03:00.

Jira → fetch cây → persist issue → engine tính rollup + snapshot → lưu daily_snapshot / group_rollup → xoá cache chart

Đọc Web → API

Đồng bộ, mili-giây. Không chạm Jira, không tính lại — chỉ lấy snapshot đã dựng sẵn (qua cache Redis).

Web mở biểu đồ → GET /api/burndown/epic/:key → đọc Postgres (+cache) → JSON zod → Recharts vẽ 3 chế độ xem

Nhóm ② — master/tham chiếu & bản ghi vận hành.

Quy ước cột

C-1 mốc thời gian dùng TIMESTAMPTZ (lưu UTC), ngày thuần dùng DATE. C-2 thời lượng lưu bằng giây, kiểu BigInt, hậu tố _s. C-3 bảng/cột snake_case ở DB, đổi sang camelCase tại tầng repository.

Chạy lại an toàn

C-6: mọi bảng job ghi đều có khoá duy nhất tự nhiên (uq_snapshot = epic+ngày, worklog_id = ID Jira…), nên chạy lại một lượt đồng bộ không nhân đôi dữ liệu.

Không xoá cứng

Issue rời Epic chỉ được đánh removed_at, không DELETE — snapshot của những ngày trước vẫn phải nhìn thấy nó. Đây là lý do nhiều bảng lịch sử nối theo khoá, không đặt FK cascade.

Prisma engineType

engineType="client" chuyển sang query-compiler WASM (đóng gói sẵn) chạy qua driver pg — không tải binary Rust từ CDN (máy dev chặn mạng). Migration viết tay, áp bằng pnpm db:migrate (không dùng prisma migrate).

Quy trình CI/CD

Một workflow GitHub Actions (.github/workflows/ci.yml) chạy trên push → main và mọi pull request. Ba job song song; job test dựng hẳn một PostgreSQL thật. Triển khai (CD) làm tay theo runbook — pipeline này thuần kiểm chất lượng.

Runner Node 22 · pnpm qua corepack · concurrency: cancel-in-progress huỷ lượt cũ khi push tiếp.

JobCác bướcChốt điều gì
typecheckinstall --frozen-lockfile → db:generate → tscKiểu đúng toàn workspace (cần Prisma Client đã generate)
lintinstall → db:generate → eslint .Gồm rule chặn import xuyên ranh giới & chặn new Date() trong engine
testservice Postgres 16 → install → db:generate → db:migrate → vitestChạy migration viết tay lên DB thật, rồi toàn bộ test — gồm nhóm ràng buộc DB (CHECK, partial index)
Gate chống xanh giả

Nếu DATABASE_URL hỏng, nhóm test ràng buộc DB sẽ skip mà CI vẫn xanh. Một bước grep chuỗi "chưa có DATABASE_URL" trong output và fail nếu thấy — buộc nhóm đó phải thật sự chạy.

Gate tốc độ

test:engine phải chạy < 10 giây (C-12) — đo bằng đồng hồ, vượt ngưỡng là CI đỏ, không phải cảnh báo. Giữ bộ test lõi đủ nhanh để dev thật sự chạy thường xuyên.

CD làm tay

Chưa có job deploy tự động. Triển khai theo RUNBOOK.md: áp migration trước (db:migrate) → db:generate → deploy code. Worker còn tự chặn khởi động nếu còn migration chưa áp (assertMigrationsApplied).

07

Năm nguyên tắc giữ hệ thống không mục

Đây là những ràng buộc được lint/test cưỡng chế, không chỉ là quy ước trên giấy.

PORTS & ADAPTERS

Một điểm lắp ráp duy nhất

server.ts / main.ts là nơi DUY NHẤT biết Prisma, Redis, Jira thật. Mọi tầng dưới chỉ thấy "cổng" ⇒ test được mà không cần dựng hạ tầng.

ENGINE THUẦN

Không IO, không đồng hồ

Engine cấm import db/jira và cấm new Date() (nhận asOfMs qua tham số). Kiểm bằng 20 golden dataset, chạy < 10 giây. ESLint chặn vi phạm.

GHI / ĐỌC

Tách hai đường

Việc dài hơi thuộc worker (phút); request đọc thuộc API (mili-giây). Nhờ vậy mở biểu đồ không bao giờ phải chờ Jira.

HÀNG ĐỢI

3 queue + rate-limit chung

sync · backfill · reconcile trên BullMQ+Redis. Token-bucket Redis dùng chung giới hạn Jira 40 req/s toàn hệ thống, không phải mỗi worker một hạn.

HỢP ĐỒNG

zod là một nguồn sự thật

Type + schema sống chung ở shared, validate ở FE lẫn BE. Lệch kiểu giữa hai đầu bị bắt ngay lúc biên dịch hoặc tại biên request.

PHÂN TẦNG LINH ĐỘNG

Tổng quát N tầng, không phá cũ

Cột group_path JSONB + bảng group_tier* cho phép 1..N tầng nhóm. Epic 3 tầng cũ giữ hành vi byte-identical; đường đa tầng chỉ bật khi có cấu hình mới.
